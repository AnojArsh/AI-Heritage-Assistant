# 🏛️ Heritage Architecture Assistant

An AI system that combines **Computer Vision** and a **LangChain Retrieval-Augmented Generation (RAG)** pipeline to classify architectural styles from photographs and answer follow-up questions about them, grounded in a curated heritage knowledge base.

Built as a prototype for the **National Heritage Preservation Trust (NHPT)** visitor knowledge support use case.

## ✨ Features

- **Image classification** — upload a photo of a building and get its architectural style predicted with a confidence score, using an EfficientNetB0 transfer-learning model fine-tuned on 6 styles (Gothic, Baroque, Byzantine, Art Deco, Bauhaus, Ancient Egyptian).
- **Conversational RAG assistant** — ask natural follow-up questions ("why does it need flying buttresses?") and get answers grounded in a curated set of heritage documents, with cited sources, rather than the LLM's unconstrained general knowledge.
- **CV → LLM handoff** — the classifier's predicted style and confidence are woven directly into the query sent to the retriever, so the assistant automatically discusses the *correct* style with no extra lookup logic.
- **Multi-turn memory** — a history-aware retriever rewrites follow-up questions into standalone queries so short, contextual questions still retrieve correctly.
- **Runs fully locally** — the LLM (Llama 3.2:3b) and embedding model (nomic-embed-text) run via [Ollama](https://ollama.com), so no images or conversation data ever leave your machine, and there's no API cost.
- **Streamlit web app** — a two-panel "inspect a building / ask the assistant" interface for interactive use.

## 🧩 Architecture

```
                 ┌────────────────────┐
   Image  ─────► │  EfficientNetB0    │
                 │  (transfer learn.) │
                 └─────────┬──────────┘
                           │ predicted style + confidence
                           ▼
          "the image was classified as '<style>'
           with <confidence>% confidence. <user question>"
                           │
                           ▼
                ┌─────────────────────┐
                │ History-aware        │◄── conversation memory
                │ retriever (LangChain)│
                └──────────┬───────────┘
                           │ standalone query
                           ▼
                ┌─────────────────────┐
                │  Chroma vector store │◄── TextBase/*.txt (6 heritage docs)
                │  (nomic-embed-text)  │
                └──────────┬───────────┘
                           │ top-k relevant chunks
                           ▼
                ┌─────────────────────┐
                │  Llama 3.2:3b (Ollama)│──► grounded answer + cited source(s)
                └─────────────────────┘
```

## 🛠️ Tech Stack

| Component | Choice | Why |
|---|---|---|
| CV model | EfficientNetB0 (transfer learning, Keras/TensorFlow) | Strong accuracy-to-compute trade-off; trains on a CPU-only 16GB machine |
| LLM | Llama 3.2:3b via Ollama | Runs fully offline/local, no API cost, no data leaves the machine |
| Embeddings | nomic-embed-text via Ollama | Local, avoids external embedding API dependency |
| Orchestration | LangChain (`langchain_classic` chains) | History-aware retrieval, document-combination chain, memory wrapper |
| Vector store | Chroma | Zero-config local persistence, no separate server process |
| Frontend | Streamlit | Fast interactive prototype UI |

## 🚀 Setup

### Prerequisites

- Python 3.10+
- [Ollama](https://ollama.com) installed and running locally
- ~4GB free disk space for the local LLM + embedding model

### 1. Clone and install dependencies

```bash
git clone https://github.com/<your-username>/<your-repo>.git
cd <your-repo>
pip install -r requirements.txt
```

### 2. Pull the local models via Ollama

```bash
ollama pull llama3.2:3b
ollama pull nomic-embed-text
```

Make sure the Ollama app/server is **running in the background** before starting the assistant — without it, embedding and generation calls will fail with a connection error.

### 3. Prepare your dataset

Update the `RAW_DATA_DIR` path in `01_data_preparation.ipynb` to point to your image dataset, organised as:

```
Data/
├── Gothic architecture/
├── Baroque architecture/
├── Byzantine architecture/
├── Art Deco architecture/
├── Bauhaus architecture/
└── Ancient Egyptian architecture/
```

Run the notebooks **in order**:

1. `01_data_preparation.ipynb` → creates the stratified train/val/test split + `dataset_metadata.json`
2. `02_modeling_training_evaluation.ipynb` → trains the classifier, evaluates it, saves `architectural_style_classifier.keras` and `class_indices.json`
3. `03_streamlit_app_generator.ipynb` → verifies the `TextBase/` folder and model files are present, generates `streamlit_app.py`

### 4. Run the app

```bash
streamlit run streamlit_app.py
```

## 📊 Results

- **Test accuracy:** 95.08% | **Weighted F1:** 0.95
- Strongest class: Ancient Egyptian architecture (precision/recall/F1 = 1.00), reflecting its visual distinctiveness
- Weakest class: Baroque architecture (F1 = 0.93)
- Confusion is concentrated within two visually coherent clusters — (Gothic, Baroque, Byzantine) and (Art Deco, Bauhaus) — with zero cross-cluster confusion, suggesting the model learned genuine style boundaries rather than shortcuts
- Grad-CAM confirms attention on diagnostic features (spires, rose windows, facade ornamentation) for correct high-confidence predictions

## ⚠️ Known Limitations

- **Closed-set classification** — the model always predicts one of the 6 trained styles, even for out-of-distribution images (e.g. a building style not in the training set). A confidence threshold is used as a partial mitigation; true open-set recognition is future work.
- **Occasional cross-style hallucination** — with a small local LLM, retrieved chunks from an unrelated style can occasionally get blended into an answer. Mitigated (not eliminated) via an explicit system-prompt instruction to ignore mismatched-style context.
- **Single-user, local-only design** — not built for concurrent multi-user throughput; would need GPU-backed or cloud-hosted inference to scale.

## 🔭 Future Improvements

- Open-set / out-of-distribution detection for the CV model
- Evaluate a larger or cloud-hosted LLM to reduce residual hallucination
- Expand the knowledge base and tune retrieval (e.g. lower `k`, add a relevance filter)
- Streamed token-by-token responses in the Streamlit UI
- GPU-backed or cloud deployment for multi-user support
